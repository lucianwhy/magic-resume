## 1. 用户目标与协作方式

项目正在为“求职智能体”实现个人中心，首期分为：

1. 固定信息：姓名、联系方式、教育、在读状态、求职状态和目标岗位。
2. 项目经历：后续支持手工填写、简历/文件解析、GitHub/Gitee 仓库分析和智能体对话补全。

用户希望通过项目学习技术，因此默认协作方式是：

- 先解释本步要解决的问题、涉及文件和设计原因。
- 给出小块、可运行的代码和明确粘贴位置，由用户自行创建和粘贴。
- 用户运行、截图或贴报错后，再解释和定位问题。
- 除非用户明确说“直接修改代码”或“帮我改”，否则不要直接改业务代码。

## 2. 仓库架构与不可违反的边界

根目录的 `AGENTS.md` 和 `docs/ARCHITECTURE.md` 是当前架构的权威说明。每次后续开发前应先阅读它们。

| 模块 | 位置 | 边界 |
| --- | --- | --- |
| Web | `apps/web/` | Magic Resume 网页和 HTTP API；个人中心前端必须放在这里 |
| CLI | `packages/cli/` | 只能通过 HTTP 调用 Web API，不能导入 Web 内部源码 |
| Skills | `skills/` | 独立安装的 `ican-*` Skills，不能依赖仓库绝对路径或 Web/CLI 实现 |
| 文档 | `docs/` | 架构、接口、开发说明和交接文档 |
| 用户职业数据 | 仓库外的 ICAN 工作区 | 不能提交简历原件、求职材料或用户隐私数据 |

Web 使用 TanStack Start。实际路由入口位于 `apps/web/src/routes/`；部分页面实现位于 `apps/web/src/app/`，这是迁移兼容结构。`apps/web/src/routeTree.gen.ts` 是自动生成文件，绝不能手动修改。

## 4. 当前前后端数据链路

```text
浏览器访问 /app/dashboard/profile
    -> apps/web/src/routes/app/dashboard/profile.tsx
    -> apps/web/src/app/dashboard/profile/page.tsx
    -> apps/web/src/features/profile/api.ts
    -> http://127.0.0.1:8000/api/v1/profile
    -> backend/app/main.py
    -> 当前内存中的 profile 变量
```

保存时：

```text
用户填写表单
    -> page.tsx 的 handleSubmit
    -> updateProfile(data)
    -> PATCH /api/v1/profile
    -> FastAPI 的 ProfileUpdate 校验
    -> 仅更新请求中携带的字段
    -> 返回最新 ProfileResponse
    -> 前端 setProfile(savedProfile)
```

`PATCH` 使用 `data.model_dump(exclude_unset=True)`，因此只提交例如 `name` 时，不会把未提交的手机号和邮箱意外覆盖为 `null`。

## 5. 本阶段重要概念

| 概念 | 当前项目中的意思 |
| --- | --- |
| `types.ts` | TypeScript 的数据契约，编译期检查，不发送请求 |
| `api.ts` | HTTP 请求封装；以后 Token、环境变量、统一错误处理放这里 |
| `page.tsx` | 可见页面和表单交互；不应直接写 SQL 或复杂后端逻辑 |
| `routes/.../profile.tsx` | URL 到页面组件的注册；不应放复杂 UI |
| `client.tsx` | Dashboard 侧栏和布局；负责入口和高亮，不保存用户资料 |
| CORS | 前端和后端端口不同，浏览器必须得到后端允许才能发请求 |
| Pydantic | FastAPI 的请求/响应数据校验与自动接口文档来源 |

## 6. 下一步建议：将内存替换为数据库

下一步不要立即做项目经历或智能体，而是完成固定信息的持久化闭环。推荐学习顺序：

1. 先在浏览器填写并保存一次，确认刷新页面后数据仍能从**当前运行的 FastAPI 进程**读回。
2. 选择并准备 PostgreSQL；建议使用 Docker Compose 启动本地 PostgreSQL。
3. 后端增加 SQLAlchemy、Alembic 和 PostgreSQL 驱动。
4. 创建 `users` 与 `profiles` 表，并用固定的演示用户替换当前 `DEMO_USER_ID`。
5. 新建 repository/service 层，将路由函数中的全局 `profile` 改为数据库读写。
6. 编写最小迁移和接口测试，确认 FastAPI 重启后信息仍保留。

建议的第一版数据表：

```sql
create table users (
  id uuid primary key,
  created_at timestamptz not null default now()
);

create table profiles (
  user_id uuid primary key references users(id),
  name varchar(100),
  phone varchar(30),
  email varchar(200),
  city varchar(100),
  school varchar(200),
  major varchar(200),
  graduation_date varchar(30),
  study_status varchar(20),
  job_status varchar(30),
  target_role varchar(200),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

在未接入登录前，`user_id` 可继续由后端固定为一个演示 UUID；但不能让前端请求体自行传入任意 `user_id`。
