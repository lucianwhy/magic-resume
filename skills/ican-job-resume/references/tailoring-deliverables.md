# 岗位定制交付方法

本文件规定岗位定制过程中四个中间产物。它们用于让选择可解释、改写可追溯；不能绕过事实台账或 `fact_id` 校验。

## 1. 岗位要求—证据矩阵

先拆 JD，再写简历。每项要求占一行：

| 字段 | 内容 |
| --- | --- |
| `requirement` | JD 原始要求或忠实归纳。 |
| `priority` | `must`、`important`、`nice_to_have`。 |
| `evidence` | 可核验事实、来源和 `fact_ids`。 |
| `fit` | `supported`、`partial`、`needs_confirmation`、`unsupported`。 |
| `action` | 保留、强化、降级表述、询问、略去。 |

同一事实可以支持多项要求，但不能因此扩大事实范围。`partial` 必须指出差在哪一层，例如“使用过 API，不等于理解模型原理”。

## 2. 关键词分级

关键词不是自动插入清单。按证据分四桶：

- `supported`：事实和证据已确认，可自然写入。
- `strengthen`：原文已有事实，但表达过弱或术语不一致，可在不扩张含义时强化。
- `needs_confirmation`：知识库存在暗示，但需要用户确认使用深度、职责或时间。
- `do_not_claim`：无证据、仅 JD 出现，或会把接触写成精通；不得写入。

ATS 匹配只决定表达顺序和同义词选择，不改变真实性门槛。

## 3. 要点改写矩阵

每条候选改写记录：

| 字段 | 内容 |
| --- | --- |
| `original` | 源简历原文。 |
| `candidate` | 候选文案。 |
| `jd_requirement` | 对应 JD 要求。 |
| `fact_ids` | 支持该文案的事实 ID。 |
| `rationale` | 为什么改：更具体、调整顺序、统一术语或压缩。 |
| `risk` | 证据边界、可能误读、需要确认的地方。 |

优先改“动作 + 对象 + 方法 + 可核验结果”。没有已确认结果时，宁可写产物或职责边界，不制造数字。

## 4. 修改日志

`change-log.md` 面向用户，至少包含：改了什么、为什么改、使用哪些证据、对应哪项岗位要求、还需确认什么。明确列出主动未加入的高频关键词及原因，防止用户误以为遗漏。

## 5. 交付检查

- 每条新增或强化主张都有 `fact_ids`。
- 每个 `needs_confirmation` 仍是问题，不进入候选简历。
- 候选版本使用新 ID，源简历和源 JSON 未被覆盖。
- `fit-report.md`、`resume-diff.json`、`change-log.md` 能解释每个实质变更。
