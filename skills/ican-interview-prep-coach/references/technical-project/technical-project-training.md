# 技术与项目综合面考前培训

## 训练目标

让用户从“听过术语、做过功能”变成能解释：业务问题是什么、技术为什么必要、核心链路如何运行、本人负责哪一层、失败时如何排查、结果如何验证、还能怎样优化。技术概念必须落到真实项目；项目叙事必须经得住技术追问。

每个主题按固定顺序训练：业务问题 → 一句话定义 → 最小架构 → 本人动作 → 关键取舍 → 常见故障 → 结果证据 → 精简版与展开版表达。术语缩写不明确时先请用户确认，不猜含义。

## 项目证据卡

未知就写未知，不能用推测填满。

| 字段 | 应回答内容 |
| --- | --- |
| 业务问题 | 谁在什么场景遇到什么低效、成本或风险。 |
| 成功标准 | 用户、业务或技术上如何判断有效。 |
| 我的边界 | 独立负责的页面、接口、模型链路、部署或协调事项。 |
| 架构与数据流 | 输入从哪里来，经过哪些服务、Agent、数据库或外部工具，输出给谁。 |
| 关键决策 | 至少一个选择及替代方案，说明为何必要。 |
| 难点与处理 | 真正遇到的问题、定位方法、解决或降级。 |
| 结果与证据 | 交付链接、代码、截图、用户数、时间、验收方式及统计口径。 |
| 边界与下一步 | 没做什么、风险是什么、会怎样迭代和验证。 |

## 四段工程叙事

1. **场景与目标**：先说用户和问题，不从技术名开场。
2. **本人贡献**：明确“我负责”，不把团队工作全部说成个人工作。
3. **技术方案与取舍**：用输入 → 处理 → 存储/工具 → 输出描述数据流，说明为什么使用该方案。
4. **验证与反思**：说结果口径、真实不足和下一步。

> 面向 `<用户>` 的 `<问题>`，我负责 `<明确模块>`。输入是 `<数据>`，经过 `<关键逻辑/系统>`，输出 `<价值>`。选择 `<方案>` 是因为 `<约束与取舍>`。通过 `<证据>` 验证；目前 `<边界>`，下一步会 `<改进及验证方法>`。

## AI 应用核心概念

| 概念 | 一句话 | 最小链路 | 项目追问 |
| --- | --- | --- | --- |
| LLM | 根据上下文预测后续 token 的模型，不是事实数据库。 | 输入 → 模型推理 → 输出 | 如何处理幻觉、随机性和不可复现结果？ |
| Prompt | 给模型的任务、约束、上下文和输出格式。 | 规则 + 用户任务 + 上下文 + schema | 如何验证提示词优化确实有效？ |
| RAG | 先检索外部资料，再把证据交给模型生成答案。 | 切分/索引 → 查询 → 召回 → 可选重排 → 上下文 → 回答/引用/拒答 | 为什么项目需要 RAG？什么情况不该用？ |
| Embedding | 将文本映射到向量空间，以语义相似度找候选资料。 | 文档与问题向量化 → 相似度检索 Top-K | 精确编号、日期和专有名词怎么处理？ |
| 混合检索 | 合并语义与关键词召回，提高不同问题类型覆盖率。 | 向量候选 + 全文候选 → 融合/去重 → 可选重排 | 项目是否真实使用？如何验证提升？ |
| Agent | 在目标、状态、工具和反馈下决定下一步动作的执行体。 | 状态 → 判断/规划 → 工具 → 观察 → 下一步或结束 | 为什么不是固定工作流？如何限制错误动作？ |
| 工作流 | 预定义步骤与路由；可以包含 Agent 节点。 | 节点 + 状态 + 条件边 + 终止条件 | 哪些步骤需要确定性，哪些允许模型判断？ |
| Function Call | 模型产出 schema 约束的参数，服务端验证后执行工具。 | 参数生成 → 校验/鉴权 → 执行 → 结果回灌 | 超时、重试、幂等和权限怎么做？ |
| MCP | 客户端与工具或资源服务端之间的标准化接入协议。 | 发现工具 → 调用 → 服务端返回 | MCP 解决了什么接入问题？它不是什么？ |

## RAG 必须讲清的八件事

1. 数据来源是否可信、可更新、有权限边界。
2. 如何切分，chunk 与 overlap 为什么合理。
3. 元数据包含来源、版本、权限、时间或科目中的哪些字段。
4. 为什么选择向量、全文或混合检索。
5. 如何控制 Top-K、去重、重排与上下文长度。
6. 证据不足时如何拒答。
7. 如何提供来源引用。
8. 如何评估检索、答案、拒答、延迟和成本。

未真实使用重排、评估集或特定向量数据库时，只能作为下一步建议，不能说成项目事实。

## Agent 必须讲清的六件事

1. 业务目标和成功条件。
2. 单 Agent 还是多 Agent，以及职责是否真的独立。
3. 共享状态包含什么。
4. 节点输入输出、路由和终止条件。
5. 工具权限、参数校验、超时、重试、幂等和人工介入。
6. 日志、链路追踪、成本、质量与失败观测。

## 后端与数据库

- FastAPI：路由、服务、数据访问、模型调用分层；区分异步 I/O 与阻塞任务；准备鉴权、超时、异常、日志和健康检查。
- 数据库：先定义查询条件、数据量和延迟目标，再讨论索引；用执行计划检查扫描、排序和索引命中；索引会增加写入成本。
- Redis：说明真实用途、key、TTL、一致性、失效及击穿/穿透处理；没有业务必要时不要为了技术栈引入。
- 消息队列：说明为什么需要异步或削峰，并准备消息丢失、重复、幂等、失败和一致性问题。

## 优化建议规则

先分开“已经完成”和“培训建议”。建议必须说明要解决的问题、代价和验证方法。

| 项目类型 | 常见优化方向 | 验证方式 |
| --- | --- | --- |
| RAG 应用 | 元数据过滤、混合检索、重排、引用校验、拒答、离线评估集 | 命中率、引用正确率、人工评测、延迟/成本 |
| Agent 系统 | 合并无独立职责节点、状态 schema、失败重试/降级、工具权限、链路日志 | 成功率、失败定位时间、成本、人工介入率 |
| FastAPI 后端 | 分层、参数校验、异步 I/O、连接池、缓存、限流、健康检查 | P95 延迟、错误率、吞吐、压测 |
| 数据库 | 索引、分页、批量读写、避免 N+1、缓存 | 执行计划、扫描行数、查询耗时 |
| 小程序/产品 | 埋点、漏斗、反馈入口、灰度、隐私说明 | 激活、留存、任务完成率、反馈 |

## 常见风险

- “独立开发”：准备需求、设计、代码、部署各环节证据，说明外部依赖。
- “300+ 用户”：准备统计定义、截止日期和后台证据；不知道活跃或留存就说未统计。
- “多 Agent”：准备每个 Agent 的职责、输入输出、路由和删除该节点的影响。
- “上线”：说明域名、部署、依赖、日志和当前可用状态；不把本地运行说成上线。
- 技术名词：必须回答项目为何需要；不需要时，承认更简单方案更合适。

## 验收产物

- 项目证据卡。
- 相关概念卡与最小数据流。
- 一份精简工程叙事和一份展开版工程叙事。
- 至少一个选型、失败模式或替代方案。
- 已做事实与优化建议分栏。
- 待补事实及证据优先级。

默认做讲解、共同整理和短练习，不自动进入模拟面试。
