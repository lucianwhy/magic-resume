# 技术面考前培训

## 训练目标

让用户从“听过术语”变成能解释：它解决什么问题、核心链路是什么、在我的项目哪一层出现、失败时如何排查、我实际做到了什么。

每个主题按固定顺序教学：一句话定义 → 最小架构 → 常见坑 → 项目映射 → 5 分钟练习。术语缩写不明确时先请用户确认，不猜含义。

## AI 应用核心概念

| 概念 | 一句话 | 最小链路 | 常见误区 |
| --- | --- | --- | --- |
| LLM | 根据上下文预测后续 token 的模型，不是事实数据库。 | 输入 → 模型推理 → 输出 | 把模型输出当作真实知识。 |
| Prompt | 给模型的任务、约束、上下文和输出格式。 | System/规则 + 用户任务 + 上下文 + schema | 只堆提示词，不定义验收标准。 |
| RAG | 先检索外部资料，再把证据交给模型生成答案。 | 入库切分/索引 → 查询改写 → 召回 → 可选重排 → 上下文组装 → 回答/引用/拒答 | “有向量库”不等于回答可靠。 |
| Embedding/向量检索 | 将文本映射到向量空间，以语义相似度找候选资料。 | 文档与问题分别向量化 → 相似度检索 Top-K | 对精确编号、日期、专有名词单独依赖语义检索。 |
| 全文检索 | 按关键词、倒排索引等寻找精确文本。 | 分词/索引 → 关键词查询 → 候选 | 忽略同义表达与语义召回。 |
| 混合检索 | 合并语义召回和关键词召回，提高不同问题类型覆盖率。 | 向量候选 + 全文候选 → 去重/融合 → 可选重排 | 只说“混合”却说不出融合与验证方式。 |
| Agent | 在目标、状态、工具和反馈下决定下一步动作的执行体。 | 状态 → 判断/规划 → 工具调用 → 观察结果 → 下一步或结束 | 多轮聊天、多个 Prompt 不必然是 Agent。 |
| 工作流 | 预定义步骤与路由；可包含 Agent 节点。 | 节点 + 状态 + 条件边 + 终止条件 | 用多 Agent 增加复杂度却无职责边界。 |
| Function Call | 模型产出受 schema 约束的工具参数；服务端验证后执行。 | 模型产出参数 → schema/权限校验 → 工具执行 → 结果回灌模型 | 让模型直接决定高风险操作，或不验证参数。 |
| MCP | 客户端与工具/资源服务端之间的标准化接入协议。 | 客户端发现工具 → 调用 → 服务端返回结果 | 把 MCP 当成模型或 RAG 框架。 |

## RAG 讲清楚的八件事

1. 数据从哪里来，是否可信、是否可更新。
2. 如何切分，为什么这个 chunk 大小和 overlap 合理。
3. 元数据包含什么，如来源、版本、权限、时间、科目。
4. 向量、全文或混合检索为什么适合该问题。
5. 如何控制 Top-K、去重、重排与上下文长度。
6. 证据不足时如何拒答或提示“未找到依据”。
7. 如何提供来源引用，避免用户把生成内容当事实。
8. 如何评估：检索命中率、引用正确性、答案正确性、拒答正确性、延迟和成本。

未真实使用重排、评估集或特定向量数据库时，只能说“下一步建议”，不能说“项目中已实现”。

## Agent 架构讲清楚的六件事

1. 业务目标和成功条件。
2. 单 Agent 还是多 Agent；多 Agent 的职责边界是否真的不同。
3. 共享状态放什么：用户输入、中间结果、来源、错误码、会话 ID。
4. 每个节点输入、输出、路由条件和终止条件。
5. 工具权限、参数校验、超时、重试、幂等和人工介入。
6. 日志、链路追踪、成本、质量与失败观测。

## 后端、数据库与查询优化

### FastAPI

- 路由层负责请求校验和响应；服务层承载业务；数据访问层隔离 SQL/ORM；模型调用与外部 I/O 独立封装。
- `async` 适合等待网络、数据库等 I/O；CPU 密集或阻塞 SDK 不能直接堵塞事件循环。
- 基础工程项：参数校验、统一异常、鉴权、超时、结构化日志、配置隔离、健康检查。

### 数据库查询

- 先定义查询条件、返回字段、数据量和延迟目标，再谈优化。
- 为 `WHERE`、`JOIN`、`ORDER BY` 的高频组合设计索引；避免无条件全表扫、`SELECT *`、深分页和 N+1 查询。
- 用 `EXPLAIN`/执行计划检查是否命中索引、扫描行数和排序；索引不是越多越好，会增加写入成本。
- Redis 适合热点、可容忍短暂不一致的数据；明确缓存 key、TTL、失效与击穿/穿透处理。

### AI 应用最小架构

```text
客户端 → API/鉴权 → 业务服务 ─┬→ MySQL/业务数据
                              ├→ Redis/缓存与限流
                              ├→ RAG 检索服务 → 文档/索引
                              └→ LLM/工具调用 → 日志与观测
```

讲架构时必须说数据如何流动、错误在哪里处理、回答依据从哪里来；不要只报技术名。

## 训练题型

- 解释题：RAG 与微调有什么区别？Agent 与工作流有什么区别？
- 设计题：为“学生期末复习”设计带引用的问答链路。
- 排障题：RAG 答案无关、接口突然变慢、缓存数据过期，按什么顺序排查？
- 取舍题：何时用单 Agent + 工具，何时考虑多 Agent？何时不该上 RAG？

先要求用户画口头数据流，再补充标准答案和改进点。每次只深入一个薄弱主题，避免概念堆砌。
